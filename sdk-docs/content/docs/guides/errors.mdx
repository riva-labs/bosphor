description: The typed error model, the two failures you will actually hit, and how to trace a store across chains when something stalls.

Every failure throws a typed error that extends `BosphorError`, so you can catch
the base class once and narrow on the concrete type. Nothing is defaulted or
fabricated on error, the throw carries the on-chain or relayer reason.

```ts
import {
  BosphorError,
  ProofTimeoutError,
  RelayerRequestError,
  RelayerUploadError,
} from '@bosphor/sdk';

try {
  await client.store(bytes, { epochs: 5 });
} catch (e) {
  if (e instanceof RelayerUploadError) {
    // e.status (HTTP), e.reason (the relayer's message), e.intentId
  } else if (e instanceof RelayerRequestError) {
    // a quote or encode call failed: e.status, e.retryAfterMs on a 429
  } else if (e instanceof ProofTimeoutError) {
    // e.intentId, e.timeoutMs; the intent may still execute, so re-poll awaitProof
  } else if (e instanceof BosphorError) {
    // any other SDK error
  } else {
    throw e; // not from the SDK
  }
}
```

The errors are exported from the core `@bosphor/sdk` and from both chain subpaths,
so any import path works.

## The errors

| Error | Thrown by | Fields | Meaning |
|-------|-----------|--------|---------|
| `RelayerUploadError` | `upload`, `store` | `status`, `reason`, `intentId`, `retryAfterMs` | The relayer rejected the out-of-band blob upload (e.g. a blob-id mismatch), or kept answering a transient status after the SDK's retries. |
| `RelayerRequestError` | `fetchQuote`, `priceQuote`, `relayerComputeBlob`, `fetchSolanaLzFee` | `status`, `body`, `operation`, `retryAfterMs` | Any other relayer call answered non-2xx: a 429 rate limit, a 503, a 400 for a bad request. |
| `ProofTimeoutError` | `awaitProof`, `store` | `intentId`, `timeoutMs` | The intent did not execute within the timeout. It may still execute; re-poll with `awaitProof(intentId)`. |
| `BosphorError` | base class | `code`, `retryable`, `retryAfterMs` | Superclass of every SDK error. Catch this to handle any SDK failure. |

`RelayerRequestError` and `retryAfterMs` arrived in `@bosphor/sdk` 0.14.0. Before
that, a failed quote was a plain `BosphorError` with the status in the message.

## Rate limits and `retryAfterMs`

The hosted relayers limit requests per IP (120 per minute for quotes and uploads,
30 per minute for `POST /blob/encode`). Over the limit they answer `429` with a
`Retry-After` header, and a full storage queue answers `503` with one too. The SDK
parses it (seconds or an HTTP date) into `retryAfterMs` on the thrown error, and
`retryable` tells you whether the same call can succeed later:

```ts
import { BosphorError, fetchQuote, TESTNET } from '@bosphor/sdk';

async function quoteWithBackoff(sizeBytes: number) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fetchQuote(TESTNET.relayerUrl, { sizeBytes, originToken: 'ETH' });
    } catch (e) {
      if (!(e instanceof BosphorError) || !e.retryable || attempt >= 3) throw e;
      await new Promise((r) => setTimeout(r, e.retryAfterMs ?? 2_000 * 2 ** attempt));
    }
  }
}
```

In a UI, show a countdown from `retryAfterMs` instead of retrying in a loop.

## No pending intent yet

Right after `submit`, the relayer may answer the upload with a `404` "no pending
intent": it only accepts bytes once its watcher has seen your on-chain intent, a
short lag after you submit. `upload()` and `store()` retry that, `429`, `5xx` and
network errors with exponential backoff that honors `Retry-After` and your
`signal`, for up to two minutes (`DEFAULT_UPLOAD_RETRY`). Only then do they throw
the last `RelayerUploadError`. Tune it per client, or turn it off:

```ts
const client = await createBosphorClientFromSigner(signer, {
  uploadRetry: { maxElapsedMs: 300_000 }, // or false for a single attempt
});
await client.upload(intentId, bytes, { retry: { maxAttempts: 3 } }); // per call
```

A terminal rejection (`409` already executed, `410` expired, `413` too large,
`422` bytes do not match the commitment) is never retried. One exception: a `409`
answering a retry means an earlier attempt was ingested (only its answer was
lost), so the upload counts as done.

## A timeout is not a loss

`ProofTimeoutError` means the proof had not landed **yet**, not that the intent
failed. The intent is on-chain and the bytes are with the relayer, so re-poll:

```ts
const { blobId, endEpoch } = await client.awaitProof(e.intentId, { timeoutMs: 300_000 });
```

## Trace a store across chains

When a store stalls, find the hop it stopped at. Every hop is public.

1. **Origin transaction.** Open `txHash` on Etherscan (Sepolia) or Solscan
   (devnet, `?cluster=devnet`). It must show `IntentSubmitted`.
2. **LayerZero delivery.** Search the same transaction hash on
   [LayerZero Testnet Scan](https://testnet.layerzeroscan.com). The message shows
   `DELIVERED` once the DVNs verified it; delivery typically takes one to five
   minutes on testnet. `INFLIGHT` means wait; `FAILED` means the destination
   could not execute it.
3. **Relayer progress.** The public intent feed shows how far the relayer got
   (`received`, `stored_walrus`, `recorded_sui`, `proof_sent`, `confirmed`):

   ```bash
   curl -s "https://api.bosphor.xyz/testnet/public/intents?limit=20"
   ```

4. **The proof.** `awaitProof(intentId)` resolves once the origin chain marks the
   intent executed. If the deadline passes without a proof, refund the escrow (see
   [Pay for storage](/docs/guides/pay-for-storage#refund-an-escrow)).

Check the hosted testnet health on [status.bosphor.xyz](https://status.bosphor.xyz).
